# asm — план CLI-менеджера AIR SDK

Дата: 5 октября 2026 года. Статус: начат Windows-прототип.

## Что делаем

Небольшой кроссплатформенный менеджер версий AIR SDK с интерфейсом пакетного менеджера:

```text
asm install 51.4
asm use --global 51.4
asm exec -- adt -version
```

Несколько версий SDK хранятся рядом. Можно выбрать версию по умолчанию и закрепить другую для отдельного проекта. Итоговый CLI должен работать на Windows, macOS и Linux, без графического интерфейса. Начинаем с Windows-батника и добавляем функции постепенно.

Главный принцип: простая структура, обычные функции, минимум зависимостей. Добавляем сложность только для конкретной функции.

## Первый этап: Windows-батник

Текущая реализация — `asm.bat` для команд, один `sdk.ps1` для чтения настроек и описаний SDK, короткий `README.md`. Используем встроенный Windows PowerShell. Начинаем с настроек существующего AIR SDK Manager:

- `asm help`, `asm --help`, `asm -h` и вызов без аргументов — справка.
- `asm --version`, `asm -v` — вывод номера менеджера: только `1.0.0`.
- `asm list`, `asm ls` — список SDK из каталога `AIR_SDKS`, прочитанного из `%USERPROFILE%\.airsdk\airsdkmanager.cfg`.
- `asm help list`, `asm list --help`, `asm list -h` — справка по списку SDK.
- `asm search [VERSION]` — каталог стабильных SDK с фильтром по ветке или полному номеру; вывод новых версий первым.
- `asm help search`, `asm search --help`, `asm search -h` — справка по поиску.

Каталог SDK указывать при каждом вызове не требуется. Проверяем его непосредственные подпапки, как AIR SDK Manager. Выводим полный номер из `air-sdk-description.xml` и абсолютный путь; сортируем по числовым компонентам. Пример настройки: `AIR_SDKS=C:\AIRSDK`.

Неизвестные команды и неподдерживаемые аргументы завершаются с понятной ошибкой. Отсутствующие настройки, пустой `AIR_SDKS` и несуществующий каталог считаются ошибкой. Пустой каталог даёт пояснение и код `0`; повреждённые описания SDK пропускаются с предупреждением. Конфиг AIR SDK Manager читаем без изменения.

```text
asm/
  asm.bat
  sdk.ps1
  README.md
  plan.md
```

Поиск через `PATH`, дополнительные каталоги и собственную конфигурацию asm оставляем следующим итерациям. `search` использует небольшой [официальный архив анонсов](https://airsdk.dev/news/archive) для быстрого получения свежих стабильных версий. Некоторые старые сборки без анонсов могут отсутствовать. Если в конфиге явно указан `API_ENDPOINT`, используем `GET /releases?types=production` этого API с проверкой JSON. Лимит запроса каталога — 15 секунд; при недоступном источнике читаем базу AIR SDK Manager или её резервную копию и указываем кеш в stderr. Следующий этап — установка SDK.

## Язык и структура кроссплатформенной версии

Для текущего этапа выбран Windows batch. Язык будущей кроссплатформенной версии пока не зафиксирован. Предложение — Go: отдельный исполняемый файл, простая сборка под разные ОС, HTTP и ZIP в стандартной библиотеке. Rust остаётся альтернативой. Скорость скачивания и распаковки зависит прежде всего от сети, диска и обработки архивов; без замеров нельзя обещать преимущество одного языка.

Предлагаемая структура для Go:

```text
asm/
  main.go       # Разбор команд, вывод, запуск выбранного инструмента.
  sdk.go        # Каталог версий, скачивание, установка и хранение SDK.
  sdk_test.go   # Проверки выбора версии и установки на небольших фикстурах.
  go.mod
  README.md
  plan.md
```

На старте достаточно двух исходных файлов. Команды разбираем стандартными средствами. Сетевую работу, установку и выбор версии оформляем небольшими функциями. Папки `internal`, интерфейсы провайдеров, плагины, база данных и отдельный сервер пока не нужны.

Если выберем Rust, сохраняем ту же простоту: `src/main.rs`, `src/sdk.rs`, `Cargo.toml`, документация. Асинхронную архитектуру вводим только при необходимости.

## Целевой интерфейс: добавляем постепенно

Ориентир интерфейса — пакетные менеджеры apt, winget и Chocolatey. Ниже сравнение по официальной документации, а не рейтинг частоты использования. Для asm сохраняем небольшой набор команд с понятным назначением.

### Сравнение с пакетными менеджерами

В примерах `PKG` — имя пакета, `VERSION` — полный номер его версии.

| Действие | [apt](https://manpages.debian.org/trixie/apt/apt.8.en.html) | [winget](https://learn.microsoft.com/en-us/windows/package-manager/winget/) | [choco](https://docs.chocolatey.org/en-us/choco/commands/) | Выбор для asm |
| --- | --- | --- | --- | --- |
| Установка | `install` | `install` | `install` | `install` |
| Удаление | `remove` | `uninstall` | `uninstall` | `uninstall`, псевдоним `remove` |
| Установленные пакеты | `list --installed` | `list` | `list` (Chocolatey 2+) | `list` |
| Поиск доступных пакетов | `search` | `search` | `search` | `search [VERSION]`, поиск сборок AIR |
| Сведения о пакете | `show` | `show` | `info` | `show [VERSION]`, псевдоним `info` |
| Установка точной версии | `install PKG=VERSION` | `install PKG --version VERSION` | `install PKG --version VERSION` | `install VERSION` или `install --version VERSION` |
| Обновление каталога | `update` | `source update` | Отдельной команды `update` в актуальном списке нет | `update` после первой версии |
| Обновление установленного | `upgrade` | `upgrade` | `upgrade` | `upgrade` после первой версии |

Версионный параметр подтверждён отдельно в документации [winget install](https://learn.microsoft.com/en-us/windows/package-manager/winget/install) и [choco install](https://docs.chocolatey.org/en-us/choco/commands/install/). `update` обновляет сведения о доступных сборках, `upgrade` устанавливает обновление SDK: эти действия имеют разные имена и назначение.

В asm управляем одним продуктом — AIR SDK, поэтому имя пакета опускаем. Пользовательская форма `asm install 51.4` остаётся основной; `asm install --version 51.4` — равнозначная форма с параметром. Разрешение сокращённого номера в последнюю сборку ветки — правило asm; у приведённых пакетных менеджеров точная версия задаётся полным номером.

### Команды

| Команда | Поведение |
| --- | --- |
| `asm search [VERSION]` | Опубликованные стабильные сборки AIR SDK; необязательный аргумент фильтрует ветку по числовым компонентам. Без аргумента показывает все стабильные сборки. |
| `asm show [VERSION]` | Сведения об указанной сборке: полный номер, дата, компоненты, размер загрузки и источник из манифеста. Без аргумента — о последней стабильной сборке. Псевдоним `info`. |
| `asm list [VERSION]` | Установленные SDK из сохранённого каталога. Необязательный аргумент версии фильтрует ветку и будет добавлен позже. Псевдоним `ls`. |
| `asm install VERSION` | Установить указанный SDK; сокращение выбирает последнюю стабильную сборку ветки, `latest` — последнюю стабильную версию. |
| `asm install` | Установить точный номер из ближайшего `.asm-version`; при отсутствии файла вывести подсказку. |
| `asm uninstall VERSION` | Удалить конкретную установленную сборку; требуется полный номер. Псевдоним `remove`. |
| `asm use VERSION` | Записать точную установленную сборку в `.asm-version` текущей папки и тем самым выбрать SDK для проекта. |
| `asm use --global VERSION` | Сохранить точную установленную сборку как пользовательскую версию по умолчанию в `~/.asm/current`. |
| `asm current` | Показать эффективную версию и источник выбора: проект или пользовательская настройка. |
| `asm path [VERSION]` | Вывести абсолютный путь к установленному SDK: указанному аргументом либо выбранному для текущего проекта. |
| `asm exec [--sdk VERSION] -- TOOL [ARGS...]` | Запустить SDK-инструмент с выбранным окружением; `--sdk` выбирает версию только для этого запуска. |
| `asm help [COMMAND]` | Общая справка либо справка по команде. Также `-h`/`--help`. |
| `asm --version` | Версия самого менеджера; версию AIR SDK показывает `asm current`. |

`use`, `current`, `path` и `exec` нужны для выбора и запуска SDK; это дополнительные возможности asm. Пользовательский выбор и выбор для проекта имеют явную область действия. `pin` в [Chocolatey](https://docs.chocolatey.org/en-us/choco/commands/) означает подавление обновлений пакета, поэтому этим именем не называем выбор SDK для проекта. В текущем батнике реализован только набор первого этапа, перечисленный выше. Поиск `search` также реализован. Остальные команды и параметры — план следующих итераций.

### Параметры

У коротких флагов нет единого значения: `-v` у apt и winget относится к версии, у choco — к подробности вывода; `-q` у [APT](https://manpages.debian.org/trixie/apt/apt-get.8.en.html) означает тихий вывод, у winget — запрос; `-h` у winget install запускает тихую установку, у apt и choco показывает справку. Для asm выбираем одно значение каждого короткого флага и приводим его в справке.

| Параметр | Где работает | Поведение |
| --- | --- | --- |
| `-h`, `--help` | Все команды | Справка без выполнения действия. |
| `-v`, `--version` | Корень `asm` | Версия менеджера. |
| `-v VERSION`, `--version VERSION` | `install`, `uninstall`, `show` | Номер SDK вместо позиционного аргумента. Сокращения разрешаются по правилам соответствующей команды; для удаления требуется полный номер. |
| `--verbose` | Все команды | Подробная диагностика в stderr; короткого `-v` нет, оно относится к версии. |
| `-q`, `--quiet` | Все команды | Скрыть сообщения о ходе работы; ошибки и запрошенные данные остаются. Несовместим с `--verbose`. |
| `-y`, `--yes` | Команды с обычными подтверждениями | Выполнить без интерактивного подтверждения. Принятие лицензионного соглашения задаётся отдельно. |
| `--json` | `search`, `show`, `list`, `current` | Вывести результат в машиночитаемом формате, без смешивания JSON и сообщений о ходе работы. Это возможность asm для скриптов. |
| `-g`, `--global` | `use` | Изменить пользовательскую настройку по умолчанию. |
| `--sdk VERSION` | `exec` | Выбрать установленный SDK для одного запуска, не меняя файлы выбора версий. |
| `--accept-license` | `install` | Явно принять соглашение AIR SDK для установки; подходит для CI. |
| `--` | `exec` | Завершить параметры asm; всё дальше относится к запускаемой программе. |

Длинные параметры поддерживают запись через пробел и знак равенства: `--version 51.4` и `--version=51.4`. Параметры команды идут после её имени; относительно позиционного номера версии их можно ставить до или после. Позиционный номер и `--version` одновременно не принимаем, чтобы исключить два разных источника выбора. У `exec` параметры asm идут перед инструментом; после имени инструмента аргументы передаются ему целиком. Поэтому краткая форма `asm exec adt -version` тоже допустима.

`--yes` отвечает на обычные подтверждения и не заменяет `--accept-license`. Это наше правило: в [Chocolatey](https://docs.chocolatey.org/en-us/choco/commands/install/) `--yes` подразумевает принятие лицензии; [winget](https://learn.microsoft.com/en-us/windows/package-manager/winget/install) имеет отдельный `--accept-package-agreements`. В неинтерактивном режиме отсутствие нужного подтверждения или принятого соглашения приводит к понятной ошибке, без ожидания ввода.

В обычном выводе данные идут в stdout, прогресс и диагностика — в stderr. При `--json` stdout содержит один JSON-результат. Код завершения: `0` — успех, ненулевой — ошибка; `exec` возвращает код дочернего процесса.

### Правила выбора версии

- AIR использует номера из четырёх компонентов: `51.4.1.1`. Сравниваем числовые компоненты, а не строки и не обычный трёхкомпонентный SemVer.
- Сокращения `51`, `51.4`, `51.4.1` выбирают максимальную подходящую стабильную сборку. `51.4` не совпадает с `51.40`.
- Полный номер требует точного совпадения. Недоступная версия вызывает понятную ошибку, без подстановки другой ветки.
- Для `install` выбор идёт по каталогу доступных SDK; для `use`, `path VERSION`, `exec --sdk VERSION` — по установленным версиям.
- В `.asm-version` и пользовательской настройке сохраняется полный номер. `asm install` по файлу воспроизводит версию, а не обновляет её.
- При запуске приоритет: `exec --sdk` → ближайший `.asm-version`, найденный от текущей папки вверх → `~/.asm/current`.
- Если выбранный SDK отсутствует, команда сообщает об этом. Автоматическое скачивание происходит только в `install`.
- Установка сама по себе не переключает выбранную версию. `use` меняет только указанный уровень настройки.
- `use --global` не перекрывает `.asm-version` проекта: после изменения глобальной настройки выводим выбранный полный номер и отмечаем, если в текущем проекте действует другое закрепление.

### Примеры

```text
asm search 51.4
asm show 51.4
asm install 51.4
asm use --global 51.4
asm current
asm exec -- adt -version

asm install 51.3
asm use 51.3
asm exec -- adt -version
asm exec --sdk 51.4 -- adt -version
```

Первые команды задают пользовательскую версию по умолчанию. `use 51.3` закрепляет другую версию для текущего проекта. `exec --sdk 51.4` позволяет разово проверить инструмент на другой установленной версии.

## Хранение и запуск

Корень по умолчанию — `~/.asm` на всех ОС; `~` означает домашнюю папку пользователя. Переменная `ASM_HOME` позволяет выбрать другой каталог.

```text
~/.asm/
  versions/
    51.3.4.3/
    51.4.1.1/
  cache/
  current          # Точный номер глобальной версии.
```

В установленном SDK сохраняем маленький файл метаданных: полный номер, платформа, источник и контрольные суммы. Каталог релизов кешируем в `cache`, ZIP-компоненты — в `cache/component/<name>/<component-version>.zip`, по схеме менеджера. Сохраняем стандартный `air-sdk-description.xml` для совместимости с AIR-инструментами.

Каждый полный номер получает собственную папку. Обновление устанавливается рядом; старый SDK остаётся доступен. Повторная установка готовой версии завершается без повторного скачивания.

`asm exec` передаёт дочернему процессу `AIR_HOME` и добавляет `bin` выбранного SDK в его `PATH`. Сохраняет stdin/stdout/stderr и код завершения инструмента. Аргументы передаются как отдельные значения. На Windows учитываем запуск `.bat`/`.cmd`, пробелы и кавычки в путях.

Сам CLI не может изменить окружение уже открытого родительского терминала. В первой версии надёжный способ запуска — `asm exec`; IDE получает путь через `asm path`. Прямые команды `adt`/`mxmlc` через оболочки или shims добавляем отдельным этапом.

Удаление требует полного номера. Глобально выбранный SDK сначала нужно переключить. Перед удалением показываем точную папку; CLI работает только внутри собственного каталога `versions`.

## Откуда получать SDK

Основа — протокол [AIR SDK Manager 1.4.0](https://github.com/airsdk/airsdkmanager-releases), проверенный по классам `AIRSDKAPI`, `AIRSDKBuild`, `AIRSDKDownloadProcess` и процессам сборки SDK. Оригинальное приложение и локальные материалы исследования хранятся отдельно от исходников asm.

### Подтверждено по коду менеджера

- База API — `https://api.airsdk.harman.com`.
- Каталог: `GET /releases?types=production`, релизы в поле `releases`.
- Подробный манифест: `GET /releases/versions/<full-version>?types=production`.
- Основной способ установки — набор ZIP из `build.components`. У каждого компонента указаны собственная `version`, `checksum` SHA-256 и `fileSize`.
- Загрузка компонента: `POST /releases/components/<name>/<component-version>`, form body `acceptedLicense=true` после принятия соглашения.
- Кеш: `cache/component/<name>/<component-version>.zip`. Готовые компоненты переиспользуются между релизами.
- Все компоненты манифеста последовательно распаковываются в один SDK. Менеджер не фильтрует их по ОС; для первой версии повторяем полный рецепт.
- Если компонентов нет, менеджер использует полный архив: объект из `urls` с `url`, `checksum`, `fileSize`, запрос к `https://airsdk.harman.com` с `license=accepted`.
- После распаковки создаётся `air-sdk-description.xml`, выполняются исправления Linux и настройка через `configure_linux.sh`, обработка карантина macOS и проверка конфигурации ADT.

В исследованном манифесте 51.4.1.1 семь компонентов: `linux`, `core-tools`, `iphone`, `air-tools`, `macos`, `window`, `android`. Сохраняем именно имена и версии из манифеста. Этот образец пригоден для проверки парсера; актуальный каталог получаем с сервера.

### Что ещё проверить

Прямые проверки 5 октября 2026 года дали HTTP 502 для манифестов и HTTP 200 с JSON-ошибкой `Sandbox.Timedout` для каталога. Небольшие пробные запросы архивов дали HTTP 403. Протокол известен, успешное скачивание SDK пока не подтверждено; первым этапом проверяем запросы и доступность на работающем API. HTTP 200 сам по себе не означает корректный ответ.

Прежняя проверка сайта возвращала для 51.4.1.1 `downloadable: false`. Это поле и старые строковые URL из API GitHub Action не заменяют подробный компонентный манифест менеджера.

Каталог shockpkg остаётся полезным для сравнения и возможного явно выбранного зеркала. Свои сервер, каталог пакетов и формат распространения для первой версии не требуются.

В asm переносим протокол, SHA-256, кеширование и последовательность сборки в обычные функции. Проверяем ошибки распаковки и коды завершения системных инструментов. Каждый полный номер SDK храним отдельно для воспроизводимости; у GUI сборки одной трёхкомпонентной версии могут обновляться в общей папке.

По умолчанию устанавливаем AIR SDK с компилятором. Flex overlay, старые Adobe SDK и дополнительные варианты оставляем на последующие версии.

## Как проходит установка

1. Разрешить запрошенную версию в точный номер, получить подробный манифест и выбрать компонентный рецепт либо полный архив для ОС.
2. Проверить доступность, требования к лицензии и готовую локальную установку.
3. Показать полный номер и источник. Принятие соглашения — отдельный явный шаг; для автоматизации предусмотреть `--accept-license`.
4. Скачать ZIP-компоненты последовательно и потоково в кеш с таймаутами, до трёх попыток и простым отображением прогресса; переиспользовать уже проверенные компоненты.
5. Проверить SHA-256 по `checksum` из манифеста. Временный файл `.download` становится готовым `.zip` только после совпадения суммы; у компонентного протокола поле обязательно.
6. Распаковать все компоненты в общую временную папку рядом с конечной. Сохранять права и необходимые ссылки; проверять, что пути и ссылки не выводят запись за пределы этой папки.
7. Создать `air-sdk-description.xml`, проверить структуру SDK и `lib/adt.cfg`, применить необходимые исправления Linux/macOS по рецепту менеджера и проверить результаты.
8. Сохранить метаданные и переименовать временную папку в конечную. Только после этого считать версию установленной.

Ошибка или отмена не затрагивает готовые SDK и выбранную версию. Одновременные изменения хранилища защищаем файловой блокировкой. При недоступной сети локальные `list`, `current`, `path` и `exec` продолжают работать.

CLI выпускаем для Windows x64, macOS x64/arm64 и Linux x64/arm64. Наличие бинарника asm не означает наличие подходящего SDK: совместимость каждого релиза проверяем отдельно. Для Linux ARM учитываем описанную в [инструкции AIR SDK](https://airsdk.dev/docs/basics/install/linux) настройку `configure_linux.sh arm64`.

## Порядок реализации

| Этап | Работа | Условие готовности |
| --- | --- | --- |
| 0. Windows-прототип | `asm.bat` + `sdk.ps1`: справка, версия, `list`/`ls` из `AIR_SDKS` в конфиге AIR SDK Manager. Короткий README. | Запускается в cmd и PowerShell; проверены реальные SDK, чтение настроек, пустой каталог и ошибки. |
| 1. Проверка API | Использовать исследованный протокол менеджера и сохранённый манифест. Подтвердить рабочие сетевые запросы, загрузку компонентов и доступность актуальной 51.4 и предыдущей ветки. | Подтверждено успешное получение каталога, манифеста и ZIP; ограничения записаны. |
| 2. Основа CLI | Зафиксировать язык, сделать `help`, `--version`, `search`, `show`, сравнение номеров и каталог хранения. | Сокращённый номер выбирает правильную сборку; ошибки понятны. |
| 3. Установка | Повторить компонентный рецепт менеджера: `install`, кеш ZIP, SHA-256, общая распаковка, описание SDK и настройка платформы. Добавить блокировку, `list`, `uninstall`. | Две реальные версии стоят рядом; общие компоненты переиспользуются; отмена не создаёт готовую установку. |
| 4. Выбор SDK | Добавить `use`, `use --global`, `current`, `path`, `exec --sdk`, установку по `.asm-version`. | В двух проектах запускаются разные SDK без взаимного влияния. |
| 5. Проверка и выпуск | Проверить ОС, пути с пробелами/кириллицей, передачу аргументов, ошибки сети и повреждённые архивы. Написать короткий README и настроить сборку релизных архивов. | На каждой заявленной платформе работают установка и `asm exec adt -version`; доступен отдельный бинарник asm. |

Для автоматических проверок используем сохранённый манифест, небольшие архивы и локальный HTTP-сервер. Проверяем четыре компонента версии, точное закрепление, JSON-ошибку при HTTP 200, обрыв скачивания, неверный SHA-256, сборку из нескольких ZIP, выход путей за каталог, конфликт установок и код завершения дочернего процесса. Реальное скачивание проверяем отдельно перед выпуском.

## После первой версии

- `asm update` — принудительное обновление кеша каталога, без установки SDK.
- `asm upgrade` — установка новой сборки с сохранением старой и явным переключением; точные правила области действия определяем перед реализацией.
- `asm doctor` — диагностика Java, выбранного SDK и настроек AIR.
- `asm env` или shims — интеграция с PowerShell, bash и zsh для прямого запуска SDK-инструментов.
- Дополнительные каталоги, чтение переменных окружения и собственные настройки asm.
- Импорт уже установленных SDK, настройки `adt.cfg` и работа с пользовательским `adt.lic`.
- Возобновление загрузки, загрузка только изменившихся компонентов, дополнения оболочек.
- Flex overlay и установка сопутствующих инструментов, включая APM.

Первый небольшой результат — рабочий батник со справкой и списком локальных SDK. Затем добавляем каталог, установку, выбор версии и запуск SDK-инструмента по отдельности. Структура остаётся небольшой, пока реальные задачи не потребуют её расширения.
